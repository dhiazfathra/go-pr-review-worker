Webhook intake as a thin adapter

Strong ports & adapters

internal/webhook/handler.go · internal/webhook/verify.go

sequenceDiagram
  participant GH as GitHub
  participant WH as Webhook Handler
  participant Q as Job Queue (chan, buf=1)
  participant W as Worker (single goroutine)
  GH->>WH: PR opened / synchronize
  WH->>WH: verify signature
  WH->>Q: enqueue ReviewJob{prID, cycle}
  Q-->>W: dequeue (blocks if busy)
  Note over W: only one job in flight, ever

Problem: webhook delivery is bursty — GitHub retries, multiple pushes in seconds — and none of that bursts logic should live near HTTP handling.

Solution: handler does nothing but verify + enqueue. All ordering, dedup, and cycle-counting logic sits behind the seam, in the worker.

  • • locality: retry/dedup logic lives in one place
  • • interface shrinks: handler is signature-verify + enqueue, nothing else

Problem: cycle count (max 2 per PR) was tracked in memory in the earlier sketch — a worker restart mid-review silently resets it, so a PR could get a 3rd review.

Solution: SQLite table pr_reviews(pr_id, cycle, status, updated_at) as the single source of truth. Worker reads/writes it; nothing else touches it.

  • • deepen: one interface (Store.NextCycle(prID)), implementation absorbs locking + persistence
  • • leverage: same interface serves crash recovery and dedup
ADR: SQLite over Postgres/Redis — single VM, single writer, zero ops overhead; matches your cost-minimal infra stance on [[erp-replatform]] and [[event-tracking-platform]].

CLI runner: claude → opencode as a swappable adapter

Strong local-substitutable

internal/reviewer/runner.go

flowchart TD
  R[ReviewRunner.Run diff] --> C{claude cli exec}
  C -->|exit 0| P[Parse output → comments + summary]
  C -->|rate limited signal| O[opencode cli exec]
  O -->|exit 0| P
  O -->|fails too| F[Mark job failed, alert]

Problem: if fallback logic is inline in the worker loop, every future engine swap (a 3rd CLI, a hosted API) means editing the worker.

Solution: one ReviewEngine interface, two adapters (claude, opencode). Worker calls the interface, never a specific binary.

  • • two adapters justify the seam: claude in prod, opencode as fallback, mock in tests
  • • locality: rate-limit detection regex/exit-code logic lives only in the claude adapter

Top recommendation: Go, single binary, SQLite-backed worker

Thin webhook adapter, one deep worker owning queue + cycle-state + CLI dispatch, one ReviewEngine seam for claude/opencode. No Redis, no external queue — a buffered channel plus SQLite covers the "1 worker, 1 job, 2 cycles" constraint entirely in-process. ↑ jump to candidates
